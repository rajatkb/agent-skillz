# Harbor (Stremio Client) Troubleshooting

Harbor = self-contained desktop client for the Stremio addon ecosystem. When the user reports streaming problems (RAM blowups, disk filling, buffering, "source not cached" errors, 1-second stutters/freezes), this skill maps the relevant code, the settings that control it, and the live-diagnosis path.

## Launching Harbor (from WSL)

- Install location: `C:\Users\<user>\AppData\Local\Harbor\Harbor.exe` (per-user Tauri install — NOT under Program Files; both `Harbor\` and `harbor\` case variants exist on disk). Start-menu entry: "Harbor" / AppID `app.harbor`.
- Launch: `powershell.exe -NoProfile -Command "Start-Process 'C:\Users\<user>\AppData\Local\Harbor\Harbor.exe'"` — returns immediately, no -Wait needed.
- Verify: `Get-Process -Name 'Harbor*'` → process `harbor`, window title "Harbor".
- Do NOT locate the exe via recursive `Get-ChildItem -Recurse` over `%LOCALAPPDATA%` — it times out (observed: 60s+). Use `Get-StartApps` (name/appid filter) or the known path above.

## Architecture at a glance
- Shell: Tauri 2 (Rust) + WebView2; Frontend: React 19 + TS; settings persist in localStorage key `harbor.settings`
- Player: embedded libmpv (native, HDR passthrough); hls.js/mpegts.js for live
- Torrent engine: librqbit (Rust) — torrents written to DISK under the app cache dir, served via local axum `/stream/{hash}/{file_id}`
- Debrid proxy: local axum server (`stream_proxy.rs`) streams RD/AD/PM/DL/TorBox URLs to mpv (reqwest, forwards Range — no whole-file buffering)
- Sidecars: stremio-server, yt-dlp
- Default branch: `beta-branch` (releases lag behind; verify code on beta first)

## The 4K HDR RAM trap (most common complaint)
Symptom: streaming a big 4K HDR remux balloons RAM to tens of GB and holds it.
Cause: Settings → Player → Play Mode → **"Download the whole file while streaming"** (`torrentFullDownload`). When ON, mpv gets `demuxer-max-bytes=48GiB`, `demuxer-max-back-bytes=48GiB`, `cache-secs=100000`, `demuxer-readahead-secs=100000` (src-tauri/src/mpv.rs ~lines 692-698).
Why: the *demuxer* cache (demuxer-max-bytes/readahead) lives in RAM — it holds demuxed packets. Only the raw *stream* cache is spilled to disk (`cache-on-disk=yes` + `cache-dir`). So the whole file gets pulled into RAM up to 48 GiB. Toggle default is OFF (defaults.ts:208).
IMPORTANT: `torrentFullDownload` is applied to ALL non-live playback, not just torrents — use-player-bridge.ts:126 passes it unconditionally, mpv.rs applies the 48GiB caps for any source. So a TorBox/debrid stream with the toggle ON also balloons RAM. Keep it OFF for debrid: normal mode = progressive stream, ~600MB cap, disk cache.
Debrid path (TorBox/RD/AD/PM/DL): the provider URL is registered in the local axum proxy (stream_proxy.rs) and mpv plays `http://127.0.0.1:{port}/s/{id}`. `handle_stream` → `forward_upstream` passes mpv's `range`/`if-range` headers to the provider and streams the body straight through (no buffering) — download+playback are inherently simultaneous; mpv spills to its disk cache. No TorBox-specific "download mode" exists in Harbor.

Fixes:
1. Turn the toggle OFF — normal mode caps at ~600MB total (demuxer 512MiB + back 64MiB + stream buffer 32MiB), stream cache on disk.
2. Keep the toggle but cap RAM: Settings → MPV → Advanced (mpv.conf), add `demuxer-max-bytes=1GiB` (+ `demuxer-max-back-bytes=128MiB`). Extra options are applied AFTER Harbor's hardcoded ones (`apply_extra_mpv_options` called ~mpv.rs:735), so user values win. Restart playback to apply.

Same toggle, SECOND failure mode (freezes, not RAM): on a throttled ~1x CDN link (typical TorBox `tb-cdn.pw` direct URL), `cache-secs=100000` + `demuxer-readahead-secs=100000` keep the true buffer lead near zero, so every CDN blip hard-freezes ~1s and skips frames instead of rebuffering. The seekbar "buffered" region shows mpv's TARGET (100000s), not real headroom — a full-looking bar does NOT prove the network is fine. The truthful read is the stats overlay (`i` → cache buffering %): if it collapses to ~0 right at each freeze, the feed is starved regardless of the seekbar.

## Other settings that affect storage/resources
- "Keep stream downloads in background" (`keepStreamDownloadsInBackground`): torrent engine keeps running after the player closes → disk + bandwidth, not RAM.
- Engine disk cap (`max_gb` in engine.json under app cache dir): historically enforced only at startup (issue #616); patched in later betas.
- Cache sweep: starts 60s after launch, every 30min; expires torrents by retention_hours / max_gb.

## Runtime diagnosis (live stutter/freeze complaints)
No repo needed — read the live artifacts:
- mpv log: `C:\Users\<user>\AppData\Roaming\app.harbor\harbor-mpv.log` — grows while playing; Harbor rewrites it per mpv instance AND deletes it when playback/session ends (the file can vanish mid-diagnosis), so grep/capture while the user is actively playing; line numbers shift and counters reset across instances.
- settings: `...\Roaming\app.harbor\settings.json` (single-line JSON; player keys: torrentFullDownload, mpvHwdec, mpvExtraOptions, directTorrentStream, keepStreamDownloadsInBackground, streamCacheMaxGb).
- cache dir: `C:\Users\<user>\AppData\Local\app.harbor\mpv-cache\`.
- Harbor RAM: `Get-Process -Name "Harbor*"` → WS_MB. ~300MB healthy; GBs = full-download trap engaged.

Stall signature — TWO readings; disambiguate with the `i` overlay's cache % BEFORE blaming the feed:
1. Feed starvation: `Discontinuous source PTS jump X -> Y` (libplacebo video gap) followed within ~2s by `Audio device underrun detected.` + `restarting audio after underrun` + `pause=yes`, AND the overlay cache % is low/collapsing at the freeze. Audio underrun + low cache = demuxer stopped receiving data.
2. Decode/render stall: SAME log signature but overlay shows cache 100% and Dropped (decode) > 0, vo 0 — the feed is fine; the hwdec decoder or present path is stalling and the audio underrun is DOWNSTREAM. Event ordering is not reliable (underrun can precede the PTS jump). Do NOT call it feed starvation on the log alone.

PTS-jump frame-count analysis (mechanical vs network): `(Y-X) * fps` (23.976 film) = frames skipped. UNIFORM whole-frame gaps every time (worked case: exactly 11.0 frames per jump, repeating every 15–100s) = MECHANICAL drop in the decode path — silent `vd` (no decoder errors), healthy cache, fixed-size gaps = frames vanish between decoder and renderer → hwdec driver issue. Variable gaps = network jitter.

Playback-thread blockers to rule out when the signature is mixed:
- Frame-capture machinery (NOT only seek preview): `harbor-cw-*.jpg` captures fire every ~6s with `seekPreviewEnabled` ON (seek-preview thumbnails) AND keep firing every ~12s with it OFF — the continue-watching/exit-snapshot path (`useExitSnapshot`, CACHE_MS=12000, render-API grabs via `mpv_screenshot_data_url`, plus trickplay). Each blocks the mpv core/render thread (log: `Run command: screenshot-to-file` → `Screenshot: '...jpg'`; `Spent ~11 ms generating shader LUT`) and can coincide with underruns. CORRELATION MIRAGE: at 6–12s capture density, ANY event is within ~8s of a screenshot — "25/27 PTS jumps near a screenshot" is expected by density alone, NOT evidence. To prove/disprove causation: kill the captures entirely (cwSnapshotRetentionDays=0 or find the gate) or do the standalone-mpv.exe split.
- Refresh matching: `playerDisplayPanel: auto/oled` can switch the panel to 24Hz for 24fps content. RULED OUT on this machine (don't re-chase it): `vo/gpu-next/win32 display-fps: 165.000000` + `Assuming 165.000000 FPS for display sync` in the log = panel at 165Hz. The libplacebo `display FPS: 23.952/24.390` line is the PRESENT RATE for 24fps content (each frame held ~7 vsyncs at 165Hz), NOT panel refresh — misreading it as a 24Hz mode wastes a whole theory. Only chase the 24Hz mode if the win32 `display-fps:` line itself shows ~24.

Audio is the canary: mpv's wasapi device buffer is only ~22ms (log: `Buffer frame count: 1056 (22000 us)` @ 48kHz). Any ≥20ms pipeline delay underruns it, while video tolerates ~500ms. `OnPropertyValueChanged`/`Changed property` on ANY endpoint (monitor HDMI/OLED audio, virtual devices) is noise — fires on any endpoint change and when mpv itself restarts audio.
Audio-side hardening (Settings → MPV → Advanced): `audio-exclusive=yes` (bypasses audiodg shared-mode mixing; audiodg CPU-seconds > ~10s per hour = mixer working overtime) or `audio-buffer=2` (tolerance). Decode A/B test: `hwdec=no` — freezes gone = GPU decode/present path; remain = audio/demuxer side.
- Hybrid-GPU trap (this machine): playback runs on the AMD iGPU (d3d11va = AMD). nvidia-smi readings (e.g. P4 / 15W) are the idle dGPU — ignore for playback diagnosis. User explicitly: "nvidia is not the problem, I am running on my AMD GPU."
- Second libmpv instance on this machine — Sucrose Wallpaper Engine (`Sucrose.Live.MpvPlayer.exe`, `C:\Users\<user>\AppData\Local\Sucrose\`, auto-starts at login) hosts its own libmpv for video wallpapers. It idles at ~500MB with a GPU context and LOOKS active — before blaming it for playback contention, check `Get-CimInstance Win32_Process | ? { $_.Name -match 'Sucrose' }` → CreationDate vs the symptom window. Exonerated Aug 2026 by start-time evidence (launched the next morning, after the stutter sessions). Also grep harbor-mpv.log for `sucrose` (never appears — log only has Harbor's mpv).

Check order for "suddenly started, I changed nothing":
1. App self-update: `(Get-Item "...\Harbor\Harbor.exe").VersionInfo.ProductVersion` + LastWriteTime; mpv build date in log header (`built on ...`). Known-good reference: Harbor 0.9.118 (Aug 2026), mpv v0.41.0-604 (May 2026).
2. GPU driver TDR: System event log for `nvlddmkm` / event 4101 ("display driver stopped responding") in the last hours — absent = not a driver crash.
3. Windows Update + Kernel-Power/PnP churn around onset — power-state changes alone don't cause feed stalls.
4. `Set property: cache-dir=... -> -3` + `[e][mkv] Failed to create file cache` → disk cache silently off (see Pitfalls).
5. Stream source in log: `Opening https://...tb-cdn.pw/...` = raw TorBox CDN direct link (throttle-prone) vs `http://127.0.0.1:port/s/{id}` = through Harbor's debrid proxy.
6. Stutter SURVIVES a full Harbor reinstall + fresh defaults → system-level, not the app. Harbor reinstall ≠ OS reboot: check `(Get-CimInstance Win32_OperatingSystem).LastBootUpTime` — a Tauri reinstall only restarts the app process; kernel/driver state is untouched. Remaining suspects: this boot's state, the hwdec decode path (overlay "Dropped (decode)" > 0), the audio engine (audiodg CPU-seconds), driver-age suspect pairs (year-old Radeon 890M vs recent chipset/PMF) — but VERIFY actual install dates via `pnputil /enum-drivers` (shows real package dates; e.g. amdpmf.sys was 05/08/2026 — installed months before the Aug 2026 onset, theory retracted). A .sys file's Created/Modified date is NOT the install date; pnputil is ground truth. Decisive tests in order: reboot OS → retest; YouTube/browser video stutters too = system-wide (display/driver/audio), only-Harbor = mpv-specific. THEN the clean split: bundled standalone `mpv.exe --no-config` (AppData\Local\Harbor\mpv.exe) on a local 4K file AND the exact stream URL → both smooth = Harbor's integration (captures/polling/embed) is the culprit (use HTML5 or file a bug report); stream-only stutters = source; both stutter = mpv engine on this system (option A/B: `video-sync=display-resample`, `audio-exclusive=yes`, `d3d11-flip=no`). Run this BEFORE cycling single-theory config fixes. Worked case + commands: references/system-level-escalation.md.

## Playback stats / HDR info
- Press `i` (default binding "playerStats", src/lib/hotkeys.ts) toggles a built-in stats overlay during playback: engine (libmpv/HTML5), resolution, fps, video/audio codec, hwdec, video/audio bitrate, dropped frames (decode/vo), cache buffering %, tracks, speed, volume. Polls mpv properties once/sec via `mpv_get_property` (src/components/player/stats-overlay.tsx). NO HDR metadata in it.
- Harbor reads `video-params/gamma` into `snap.hdrGamma` ("pq"/"hlg" = HDR, mpv.rs:181,805) and `video-params/primaries` (bt.2020, mac only) but never surfaces them in the UI — used internally for SDR-boost gate (use-sdr-boost-gate.ts) and native-HDR mode. HDR "quality" info visible to user = stream badges from addon metadata (Settings → Stream Badges).
- mpv's own `i`/Shift+I stats are UNREACHABLE: `input-default-bindings=no` (mpv.rs:362) and the extra-options layer blocks `input-`, `script`, `load-scripts` properties (mpv_property_blocked, mpv.rs:1077). So no stats.lua/input.conf trick via the Advanced mpv.conf panel. No external-player launch either (unlike stock Stremio) — playback is always embedded libmpv.
- If user needs real HDR metadata (primaries/transfer/peak nits): open the same file in standalone mpv (`Shift+I`) or MPC-HC+madVR — or request the feature; the data is already fetched internally.
- Frontend JS is embedded COMPRESSED inside `AppData\Local\Harbor\harbor.exe` (~162MB): UI strings that MUST exist (localStorage key `harbor.settings`, `localStorage`) return 0 `grep -abo` hits on the binary → no plaintext bundle to surgically patch. A hardwired feature with no user toggle (e.g. the CW-snapshot grab loop) CANNOT be disabled by binary edit — only the supported settings, an upstream fix, or the HTML5 engine. Don't promise a patch path that doesn't exist.

## Pitfalls
- PRESENT-STALL TRAP (the big one, Aug 2026 — cost hours): "picture freezes ~1s, audio continues" = a PRESENTATION STALL — the swapchain stops updating while mpv keeps playing. It produces NO log events (no `Discontinuous source PTS jump`, no dropped frames, no underruns, no cache/network lines) — a session can be log-CLEAN and still feel broken. Do NOT trust log metrics over the user's symptom, and do NOT call a session "clean" from the log alone. ASK THE AUDIO QUESTION FIRST: "does the audio keep playing during the freeze?" Yes + picture-only → present stall → the mpv log is the wrong evidence source; chase what the app does to the present path (frame grabs/readbacks) or the system present path (D3D11/DWM on hybrid GPUs, mpv #15196 class). Frame-drop signatures (uniform PTS jumps, `Dropped (decode)` climbing) are a DIFFERENT bug class — matching them to a present-stall symptom sends the investigation down the wrong path (happened here: hours spent on PTS-jump forensics while the user's freezes never logged).
- Torrent playback does NOT hold the file in RAM by default — librqbit `AddTorrentOptions` defaults to `write: true` (disk). RAM = librqbit piece cache + mpv caps.
- Debrid playback goes through the local proxy which streams; it does not buffer the whole file. PR #939 capped metadata-fetch buffering at 16 MiB (not the media proxy).
- mpv cache-on-disk (mpv manual): cache file is append-only, deleted when playback closes; packet *metadata* still in memory.
- User-visible settings keys live in `src/lib/settings/defaults.ts` / `types.ts`; UI labels in `src/views/settings/**` — grep those to find the exact toggle name for a setting.
- mpv `cache-dir` is an init-only option: Harbor sets it at runtime → mpv returns -3 (MPV_ERROR_PROPERTY_UNAVAILABLE, logged as `Set property: cache-dir="..." -> -3`) → `[e][mkv] Failed to create file cache` (and `[e][lavf]`) → cache-on-disk silently disabled, all buffering in RAM. Do NOT trust the seekbar after this; use the `i` overlay cache %.
- The seekbar "buffered" region lies when `torrentFullDownload` is ON: with cache-secs=100000 it renders mpv's readahead TARGET, so it can look fully buffered while actual headroom is seconds. "It's buffered, so it can't be the network" is not a valid counter-argument — verify with the `i` overlay.
- TorBox CDN direct links (`tb-cdn.pw`, esp. `indi`/India nodes) throttle/stall at peak hours; a first stream URL that fails to open (`Opening failed or was aborted`) with a direct tb-cdn fallback is a TorBox-side degradation signal, not a local one. Fix: change CDN node in the TorBox dashboard, or pick a different addon/stream.
- TorBox direct CDN URLs ALSO EXPIRE: reusing a URL logged minutes-to-hours earlier gives `HTTP error 400 Bad Request` — the standalone-mpv.exe stream test fails with the log's URL. Grab a FRESH one instead: run a watcher on harbor-mpv.log for a new `Opening https://...tb-cdn.pw/dld/...` line while the user starts playback in Harbor (launch within ~2s), or fall back to a local 4K file. Invocation gotcha (PowerShell): a bare quoted path + args is a parse error (`Unexpected token 'no-config'`) — must use the call operator: `& 'C:\Users\<user>\AppData\Local\Harbor\mpv.exe' --no-config '<url>'`. From WSL, execute the exe path directly (`/mnt/c/Users/<user>/AppData/Local/Harbor/mpv.exe --no-config "url"`).
- User pushback trap: `torrentFullDownload`'s name sounds torrent-only, so naming it as a factor for a DEBRID stream gets pushback ("why would you point to that"). Lead with the log receipt — `demuxer-max-bytes="48GiB"` set in the same session that opened the `tb-cdn.pw` URL — not the code-path claim (use-player-bridge.ts:126). Same for "it's buffered": the seekbar renders the 100000s target; the `i` overlay cache % is the truthful read.
- Harbor FULL REINSTALL reverts settings.json to defaults: API keys emptied (tmdbKey, tbKey, rdKey, ...), torrentFullDownload reset to false, custom stream filters cleared — user must re-enter keys. Two settings stores can diverge after reinstall/migration: Roaming\app.harbor\settings.json (API keys, Tauri side) vs WebView2 localStorage key `harbor.settings` (EBWebView\Default\Local Storage\leveldb — binary; `strings`/`grep` the .log file).
- VERIFY a settings change actually took effect before accepting "I tried that": mpv options apply at PLAYER INIT — a UI toggle not followed by a playback restart does nothing, and the user may have reverted it. This session: hwdec=no was reported "tested" while the log still showed `Using hardware decoding (d3d11va)` and settings.json said `mpvHwdec:"auto"`. Ground truth = mpv log (grep `Using hardware decoding` / the `Set property:` lines) + the settings.json value, not the user's report.

## ACTUAL ROOT CAUSE — CONFIRMED CLOSED (Aug 10, 2026, G14 GA403): RTSS (RivaTuner) D3D11 present-hook stalls
Symptom: periodic ~1s PICTURE freeze during playback, audio continues, nothing in the log (present stall, not frame drops). HTML5 smooth, standalone bundled mpv.exe --no-config smooth, EVERY Harbor config/version/engine-mode fails. FIXED by killing/removing RivaTuner Statistics Server (RTSS, ships with MSI Afterburner).
Mechanism: RTSS hooks D3D11 Present() to draw overlays/enforce frame limits; on the embedded libmpv swapchain it blocked Present 100-554ms in a periodic pattern. Diagnosed via mpv `--dump-stats=...` in mpvExtraOptions: video-flip start/end deltas — normal flips ~400µs median, stalls 100-550ms every ~1.04s (RTSS ~1s timer cadence), render events continuing during the stall (render-only, present blocked). Grab loop and cache-dir bugs were NOT the cause (47 stalls vs 4 grabs in a window).
DECISIVE A/B (same session, same stream, same config — only RTSS removed): BEFORE 19 stalls/50s max 513ms → AFTER 0 stalls/38s max 8ms. User identified RTSS (the logs only narrow to "present call blocks on an external ~1s timer"); the A/B confirmed it. Standalone mpv.exe was smooth because RTSS hooks per-process (it ships an mpv.exe template that disables hooking; Harbor.exe was hooked, mpv.exe wasn't).
PERMANENT FIX — RTSS ignore rule: create `C:\Program Files (x86)\RivaTuner Statistics Server\Profiles\Harbor.exe.cfg` containing `[Hooking]` / `EnableHooking\t\t= 0` (tab-separated, ASCII) — identical to RTSS's OWN shipped templates for mpv.exe/VLC/MPC-HC. Needs admin (elevated Set-Content or Notepad-as-admin; UAC via WSL Start-Process -Verb RunAs may get declined — hand the user the manual steps). Profile is read at process LAUNCH → restart Harbor after creating. Reinstall of RTSS/Afterburner may reset Profiles.
CLEANUP after diagnosis: remove BOTH `d3d11-flip=no` (TESTED — did NOT fix, 19 stalls/50s remained, blit model exonerated; AND it costs HDR10 passthrough, flip model is required for HDR metadata on Windows) and `dump-stats=...` (diagnostic only, writes multi-MB Temp file) from mpvExtraOptions. Leave `cache-on-disk=no` (hygiene for the cache-dir -3 bug).
Check: `Get-Process | ? { $_.ProcessName -match 'rtss|afterburner|encoder' }`; stall signature in dump-stats video-flip durations (run scripts/mpv-stats-analyze.py). Full case: references/rtss-present-stall.md.

## FINAL FINDING (Aug 10, 2026, G14 GA403): D3D11 Present() blocking — proven by --dump-stats
Per-frame Present() timing via `--dump-stats` (add `--dump-stats=C:\...\mpvstats.txt` to Settings → MPV → Advanced; runtime-settable, works mid-session) settled the mechanism:
- `video-flip` events = the D3D11 Present call. Measured: 2151 normal flips, median **393µs**; **47 flips took 100–554ms** — those are the freezes (picture stalls, audio continues).
- DURING a stall: render/video-draw/hwdec-map events CONTINUE (rendering works), audio-diff stays ±1ms (A/V sync fine) — only video-flip never completes until the stall ends → swapchain Present() blocks = flip-model queue-full / DWM not consuming buffers.
- Stall cadence: inter-stall gaps are exact multiples of 25 frames (~1.04s) — matches Harbor's WebView2 UI ~1s update churn (seekbar/time-pos re-renders) contending with the embedded child window's presents. mpv #15196 class (Windows 11 D3D11 present-path stutter).
- Grab loop EXONERATED as primary: 4 screenshot grabs vs 47 stalled flips in the same window. The 12s grab is a real separate bug, not this freeze.
- `hwdec-map` is a NORMAL per-frame event (~849 maps ≈ 843 flips) — NOT a screenshot/readback marker; don't reuse that assumption.
- User's "even on lower quality it freezes" is consistent: the stall is present-path, content-independent.
- TESTED-AND-FAILED levers (both, before the RTSS resolution): `playerMpvEmbed=false` (user claimed twice, settings.json showed `playerMpvEmbed:true` both times — then finally confirmed: unembedded Harbor mpv STILL stalls, so the embed path is exonerated too) and `d3d11-flip=no` (blit model — STILL 19 stalls/50s, max 513ms; flip-model queue-blocking exonerated). The present-path stall survived every config → the fault was OUTSIDE mpv: see ACTUAL ROOT CAUSE — CONFIRMED CLOSED (RTSS present-hook).
- The grab-loop theory was the second false root cause this session; the first was the LUT/HDR-churn (real contributor, not the cause). Lessons: (1) present stalls produce NO log events — measure the present path directly with dump-stats instead of chasing log signatures; (2) count events before correlating (18 stalls/40s vs 12s grab period = impossible); (3) verify settings changes actually applied before accepting a negative test result.
